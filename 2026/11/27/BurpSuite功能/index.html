BurpSuite功能

Posted on 2026-11-27

BurpSuite 基础功能及使用【模拟面试补充欠缺】

BurpSuite 七模块

Proxy

拦截和查看经过代理的请求与响应。

Repeater

（重放请求）

Intruder

参数化批量请求。

四种攻击模式的区别：

模式 说明
Sniper（狙击手） 使用一组 Payload，每次只替换一个参数位置，但可以依次测试多个位置
Battering ram（攻城锤） 使用一组 Payload，同一次请求中，所有选中的参数位置使用相同的值
Pitchfork（叉子） 使用多组 Payload，各组按照相同的序号同步取值
Cluster Bomb（集束炸弹） 使用多组 Payload，对各组数据进行所有可能的组合

Decoder

类型 说明
Base64 不是加密，不提供保密性。主要用于将二进制数据转换为便于传输的文本
URL 主要用于避免特殊字符在 URL 传输和解析过程中产生歧义
MD5 属于单向摘要算法，输出固定为 128 位
AES 对称加密，可用于文件加密、数据库加密，也可用于网络通信加密，例如 TLS 中的 AES-GCM

Comparer

对比两端数据看差异。

Scanner

自动化扫描。

两种扫描方式：

  • Passive（被动）：分析已有请求，不主动发包。
  • Active（主动）：在生产环境中主动扫描风险，可能带来以下问题：
    • 请求量过大
    • 意外修改或删除业务数据
    • 触发账号锁定机制
    • 触发 WAF/IDS 安全告警
    • 消耗服务器和数据库资源
    • 触发邮件/短信等真实业务操作

Collaborator

通过部署在其域名服务器上的 DNS 服务，检测目标系统是否触发了对外的域名解析或 HTTP 交互，常用于检测盲注、SSRF、外带数据等无法直接观察回显的漏洞。

Setting – Session

  • CookieJar：Burp 自动保存和更新从服务器收到的 Cookie。
  • SessionHandlingRules：一套规则，决定在发请求前要不要自动更新 Cookie / 加头 / 跑登录流程。
  • Marco（宏）：
    • 把一串请求录下，比如先登录再跳转；
    • 让 Burp 在后台自动重放以刷新会话或 Token；
    • 再将新值交给规则去用。

场景分析

1. Repeater 响应长度每次不同

Repeater 重放同一个请求，状态码都是 200，但响应长度每次不同，你觉得可能原因是什么？怎么排除正常业务差异，避免误判成漏洞？

  • 多次发正常请求，建立响应基线；
  • 用 Comparer 找出具体差异字段，识别并排除动态字段；
  • 结合响应头、业务状态码和实际响应内容，判断差异是否具有稳定性和业务意义。

2. HTTPS 证书不受信任

假设你已经配置好了浏览器代理，访问 HTTP 网站时 Burp Suite 可以正常抓包，但访问 HTTPS 网站时浏览器提示证书不受信任。

  • 为什么会出现这种情况？
    • 因为浏览器收到的并不是目标服务器原本提供的证书，而是 Burp 动态生成、由 Burp 自身 CA 签发的证书。浏览器默认不信任这个 CA，因此会提示证书异常。
  • Burp Suite 为什么能够查看 HTTPS 加密通信中的明文内容？
    • Burp 本质上采用了中间人代理机制，也就是 MITM。它分别建立两条独立的 TLS 加密连接：
      • 浏览器与 Burp 之间的 TLS 连接；
      • Burp 与目标服务器之间的 TLS 连接。
    • Burp 作为两条连接的端点，可以解密收到的数据，查看 HTTP 明文，再重新加密并转发。
  • 浏览器信任 Burp CA 证书的作用又是什么？
    • 它是让浏览器能够正常验证 Burp 签发的证书，而不是让浏览器跳过证书验证。HTTPS 通信仍然是加密的。

3. HTTP History 无请求记录

假设你在授权测试环境中使用 Burp Suite，浏览器能够正常访问网站，但 Proxy 的 HTTP History 中没有任何请求记录。你认为可能有哪些原因？你会按照什么顺序排查？

  1. 浏览器代理设置：检查代理 IP/端口是否正确，是否存在代理绕过规则。
  2. Proxy Listener：检查 Burp 的代理监听器是否正常运行，监听地址和端口是否与浏览器配置一致。
  3. HTTP History Filter：检查是否设置过滤条件导致请求记录被隐藏。
  4. 交叉验证：使用 Burp 内嵌浏览器访问授权测试页面，判断是外部浏览器配置问题还是 Burp 自身问题。
  5. 证书检查：如果只有 HTTPS 请求异常，再检查 CA 证书及 TLS 连接。

4. 第三方域名请求与 Scope

假设你正在对一个获得授权的 Web 应用进行安全测试，但在 HTTP History 中发现了大量第三方域名的请求，例如 CDN、广告服务和第三方登录服务。

  • Burp Suite 中的 Target Scope 有什么作用？
    • Target Scope：定义哪些域名/IP/端口/URL 路径属于目标测试范围；
    • Proxy：负责代理浏览器的 HTTP/HTTPS 流量；
    • HTTP History Filter：负责筛选已经记录的请求和响应，决定哪些记录显示在界面上。
  • 将某个域名加入 Scope 后，是否意味着 Burp 不再记录其他域名的流量？
    • 并不是，只意味着减少无关流量干扰。
  • Target Scope 与 HTTP History Filter 有什么区别？
    • 前者管范围，后者管显示。

5. Repeater 请求返回 401

假设你在授权测试环境中使用 Repeater 测试一个需要登录的接口。刚开始请求能够正常返回业务数据，但过了一段时间，同一个请求却返回了 HTTP 401，或者跳转到了登录页面。

  • 可能是什么原因？
    • Cookie 有效期；
    • 服务端 Session 可能已经失效；
    • Token 可能有过期时间 / 被撤销 / 签名校验失败（看响应的字段或 JWT 的 exp）。
  • 如何判断是 Session 过期、Token 失效，还是其他身份认证问题？
    • Session 过期：服务端保存的会话可能已经失效，即使浏览器中的 Cookie 仍然存在，也不代表登录状态有效。
    • Cookie 过期：可以通过 Expires 和 Max-Age 属性判断有效期，但 Cookie 的有效期不等于服务端 Session 的有效期。
    • Token 失效：可能是有效期届满、服务端主动撤销或者签名验证失败。如果是 JWT，可以查看其中的 exp 字段，了解其过期时间。
    • 抗重放机制：服务端可能通过时间戳、Nonce 等机制拒绝重复请求，但拒绝请求不一定会导致用户退出登录。

6. 刷新 Token 场景

假设你在授权靶场里，每次请求前都要先访问一个刷新接口才能拿到新 Token，否则就 401。你会在 Burp 里用哪几个功能配合解决？

  • Marco 记录流程；
  • SessionHandlingRules 定义什么时候跑流程；
  • CookieJar 保存和管理 Cookie。

7. Session ID 随机性

假设某个 Web 应用每次登录都会生成一个新的 Session ID。

  • 为什么 Session ID 必须具备足够的随机性？
    • Session ID 是识别用户会话的重要凭据。如果可以被预测，就可能导致其他用户的会话被冒用。
  • 如果 Session ID 仅仅由当前时间戳或者用户 ID 生成，会存在什么安全风险？
    • 即使使用 SHA-256 对时间戳或者用户 ID 进行哈希，也不代表生成的 Session ID 足够安全。哈希算法不会凭空增加输入信息的随机性。
  • Token 的长度足够长，是否就意味着它一定足够安全？
    • 即使一个 Token 有 256 位长度，如果其中绝大部分内容都是固定的，其实际随机性仍然可能很低。

8. 三种 Content-Type 的区别

假设你在 Burp Suite 中观察到一个 POST 请求，其中的 Content-Type 分别可能是 application/json、application/x-www-form-urlencoded 和 multipart/form-data。

  • 这三种 Content-Type 有什么区别？
    • application/json：使用 JSON 格式组织数据，支持对象、数组、嵌套结构等，常用于 REST API、前后端分离的 Web 应用。
    • application/x-www-form-urlencoded：采用键值对的形式组织数据，不同参数之间使用 & 符号连接，常用于传统 HTML 表单提交（例如登录、注册）。虽然与 URL 查询参数的格式相似，但也可以放在 POST 请求体中。
    • multipart/form-data：将请求体划分为多个部分，通过 Boundary 分隔，每个部分可以具有独立的请求体描述信息。常用于文件上传，也支持普通文本字段，并非只能传输文件。
  • Content-Type 和 Accept 请求头又有什么区别？
    • Content-Type：表示当前消息体实际采用什么数据格式；
    • Accept：表示客户端希望接收什么格式的响应。

9. Cookie / Set-Cookie / Authorization

请你解释 Cookie、Set-Cookie 和 Authorization 这三个 HTTP 头部字段分别有什么作用。

  • Cookie：客户端向服务器发送已保存的 Cookie，可以用于维持登录状态，也可以保存其他状态信息。
  • Set-Cookie：服务器通过响应头通知浏览器创建、更新或者删除 Cookie。
  • Authorization：客户端用于提交身份认证凭据，例如 Bearer Token，并不是直接检查用户权限。具体权限仍然由服务端判断。

10. HttpOnly / Secure / SameSite

Cookie 中的 HttpOnly、Secure 和 SameSite 这三个安全属性分别用于防范什么风险？它们能否相互替代？

  • HttpOnly：禁止 JavaScript 通过常规接口读取 Cookie，降低 XSS 导致 Cookie 被窃取的风险，但不能防止 XSS 本身。
  • Secure：限制 Cookie 通过 HTTPS 发送，降低明文传输造成的泄露风险。
  • SameSite：限制浏览器在跨站请求中携带 Cookie，主要用于降低 CSRF 风险。
  • 三个属性不能相互替代，针对的是不同安全风险。

11. 存储型 XSS 与三个属性

假设一个网站的 Session Cookie 同时设置了 HttpOnly、Secure 和 SameSite=Strict，但这个网站仍然存在存储型 XSS 漏洞。这三个属性能否彻底消除 XSS 带来的安全风险？为什么？

不能。HttpOnly 可以降低 Cookie 被窃取的风险，但无法阻止恶意 JavaScript 执行；Secure 可以保护 Cookie 的传输过程，但无法阻止 XSS；SameSite 可以降低 CSRF 风险，但 XSS 本身可能发生在网站内部，因此仍然存在风险。

12. Collaborator 收到 DNS 交互但无 HTTP 交互

Collaborator 收到了 DNS 交互记录，但没有收到 HTTP 交互记录。

  • DNS 交互能够证明什么？
    • 目标环境里某位置触发了对外的域名解析
    • 有外带行为迹象
  • 没有收到 HTTP 交互可能是什么原因？
    • 只能出网 DNS
    • 被网络策略拦截 HTTP
    • 漏洞触发点只触发解析、不访问 URL
